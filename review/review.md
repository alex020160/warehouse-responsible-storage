### Замечание к Софье № 1: Проверять конечность значений измерений и границ норматива

Issue: https://github.com/fufSonya/practice/issues/1

Полный опубликованный текст:

Рецензирование КТ3. Коммит: 320122e1498c091db1bfb36c5acea38c49bc74f0, ветка main.

Место: src/java/Main.java, Control.checkData(), строки 357–390; аналогичный пропуск есть в src/validation.py.

Демонстрационный сценарий работает, вывод Java и Python совпадает. Небольшое замечание: валидатор принимает NaN и бесконечности как корректные числовые данные.

Воспроизведение в Java-классе того же default package:
```java
var date = java.time.LocalDate.parse("2026-10-20");
var ph = new Indicator("pH");
var c = new Control(1, date, new ResponsibleEmployee(101));
c.registerResults(java.util.List.of(new Sample(1, date,
    java.util.List.of(new Reading(ph, Double.NaN)))));
System.out.println(c.checkData(java.util.List.of(new Standard(ph, 6.0, 9.0))));
```
Фактически: [] — ошибок нет. Аналогично проходят Double.POSITIVE_INFINITY в измерении, Double.NaN в минимуме и границы -Infinity/+Infinity.

Предложение: добавить Double.isFinite() для значения измерения и обеих границ; в Python — math.isfinite(), чтобы сохранить одинаковое поведение. Если бесконечности задуманы как специальное обозначение отсутствующей границы, явно описать это правило; NaN отклонять в любом случае. Достаточно локальной правки и небольшого сценария проверки.

Мой ответ и решение: замечание принято и исправлено 24.11.2026. JsonReader проверяет уникальность имён в каждом объекте до построения JsonObject.

Проверка исправления: исходное воспроизведение теперь даёт отказ. Шесть отрицательных проверок исходного JSON (включая повтор capacity с разными/одинаковыми значениями, экранированное имя и повтор поля корня), повторное чтение правильного JSON, сборка JDK 21 и 41 сохранённый сценарий прошли.

### Полученное замечание № 2: [КТ3] Неудачная регистрация через ReceivingService оставляет запись в модели

Рецензент: Деревенец Софья Олеговна (fufSonya).

Issue: https://github.com/alex020160/warehouse-responsible-storage/issues/2

Полный текст Софьи:

Проверяемый коммит — [`a37dec606983dca0510f6b829b9ebb05fab0591c`](https://github.com/alex020160/warehouse-responsible-storage/commit/a37dec606983dca0510f6b829b9ebb05fab0591c)
Место — [`src/java/src/main/java/ru/mirea/warehouse/application/ReceivingService.java`](https://github.com/alex020160/warehouse-responsible-storage/blob/a37dec606983dca0510f6b829b9ebb05fab0591c/src/java/src/main/java/ru/mirea/warehouse/application/ReceivingService.java#L32-L38)

### Проблема

`registerExpectedDelivery()` проверяет только наличие даты до изменения модели. Дата с нулевым годом вызывает исключение при завершающей проверке, когда поставка и её позиции уже добавлены. Консоль защищена работой с копией, но прямой вызов сервиса оставляет объект `Warehouse` в некорректном состоянии.

### Воспроизведение

Загрузить демонстрационный `warehouse.json`. Вызвать `registerExpectedDelivery("C001", LocalDate.of(0, 1, 1), items)` с одной позицией `P001` и ожидаемым количеством `1`. Метод выбрасывает `IllegalArgumentException` («Неверная дата»), количество поставок увеличивается с 7 до 8, повторная проверка модели снова выдаёт ошибку.

### Ожидаемый результат и исправление

Отклонять дату до первого изменения `Warehouse`, применив ту же проверку года, что и при чтении JSON. Добавить тест на прямой вызов сервиса, который проверяет исключение и неизменность модели. Для операций с несколькими изменениями можно также проверять результат на копии до публикации.

Мой ответ и решение: замечание принято и исправлено 24.11.2026. Проверка даты через IntegrityValidator.parseDate перенесена до первого изменения модели.

Изменения: ReceivingService.registerExpectedDelivery; аналогичная защита recordActualReceipt, acceptDelivery и registerPlacement. Необязательный срок годности null сохранён. Проверки выполняются и при прямом вызове сервиса, без консольной копии.

Проверка исправления: для годов 0, −1, 10000 и отсутствующей обязательной даты выполнено 15 прямых вызовов четырёх операций. Каждый отклонён, полная JSON-сериализация состояния до/после совпала, целостность подтверждена. В исходном сценарии число поставок осталось 7 вместо изменения 7→8. Годы 0001 и 9999 приняты при регистрации ожидаемой поставки; 41 сохранённый сценарий прошёл.

SHA исправления: [bc72f22c1046bdcb0e519c221f2838447a4d8521](https://github.com/alex020160/warehouse-responsible-storage/commit/bc72f22c1046bdcb0e519c221f2838447a4d8521).

### Полученное замечание № 3: [КТ3] Сверка Java и Python проходит при неполном наборе результатов

Полный текст Софьи:

Место — [`docs/compare_versions.py`](https://github.com/alex020160/warehouse-responsible-storage/blob/a37dec606983dca0510f6b829b9ebb05fab0591c/docs/compare_versions.py#L82-L99)

### Проблема

`zip(cases, python, java)` обрезает последовательности по самой короткой. Если Java вернула меньше результатов, отсутствующие сценарии не проверяются, а скрипт завершается успешно.

### Воспроизведение

Запустить `docs/compare_versions.py` через временную обёртку над `java`, которая после выполнения `VerificationMain` удаляет последний элемент из выходного JSON. Скрипт завершился с кодом 0 и вывел `40/40 совпали` при 41 входном сценарии.

### Ожидаемый результат и исправление

До сравнения проверить, что количество входов и результатов обеих версий совпадает. При расхождении завершать проверку с ошибкой и явно выводить ожидаемое и фактическое число результатов.

Мой ответ и решение: замечание принято и исправлено 24.11.2026. До zip проверяются формат массива и точное число результатов обеих версий относительно входных сценариев; пустой набор сценариев не считается успешной проверкой.

Изменения: docs/compare_versions.py, воспроизводимая проверка docs/verify_comparison_guard.py, инструкция src/java/README.md. При ошибке используется ненулевой выход независимо от assert; прежний parity-results.json удаляется перед запуском, чтобы не показывать устаревший успех.

Проверка исправления: стенд запускает настоящую Java, затем намеренно изменяет её выходной JSON перед чтением скриптом. 41 результат принят (код 0); 40, 0, 42 и объект вместо массива отклонены (код 1). При ошибке числа сообщаются явно, ложного сообщения «совпали» нет. Отдельный запуск без подмены: 41/41 сценарий Python 3.13.7 и Java 21 совпал, включая полное состояние и JSON I/O.

SHA исправления: [68b49f1136b170eac2d51f1c40e4b131a3e50e09](https://github.com/alex020160/warehouse-responsible-storage/commit/68b49f1136b170eac2d51f1c40e4b131a3e50e09).
