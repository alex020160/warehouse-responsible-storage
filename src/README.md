# Приёмка товара на ответственное хранение

Процедурный прототип аналитического этапа КТ2: от регистрации ожидаемой
поставки до регистрации размещения согласованно принятой партии.
Сотрудник подтверждает документы, вводит результаты осмотра и согласование
с клиентом; кладовщик подтверждает фактическое размещение.

## Запуск

Требуется **Python 3.13**. Используется только стандартная библиотека;
устанавливать внешние пакеты не нужно.

Из корня репозитория:

```console
cd src
python --version
python main.py
```

Проверка исправленной версии: Python 3.13.7, Windows.
Путь к данным определяется относительно `main.py`, поэтому также можно
выполнить `python src/main.py` из корня репозитория.

## Меню

```text
1. Зарегистрировать ожидаемую поставку
2. Сопоставить фактическое поступление с ожидаемой поставкой
3. Зарегистрировать расхождения
4. Подобрать место хранения
5. Зарегистрировать размещение товара
6. Просмотреть данные
0. Выход
```

Пункт 1 создаёт поставку и её ожидаемые позиции. Пункт 2 запрашивает
подтверждение наличия поставки и документов, сохраняет фактическую дату и
количества и показывает результат сопоставления. Пустая строка фактических
позиций означает полное непоступление товара; пропущенная ожидаемая позиция
получает фактическое количество 0.

Пункт 3 регистрирует количественные и, при необходимости, качественные
расхождения. После подтверждения согласования он запрашивает принятые
количества и реквизиты партий. Отказ от принятия сохраняет зарегистрированные
расхождения, но не создаёт партии. Для продолжения согласования используйте
пункт 3 повторно: существующие качественные отклонения сохраняются, а
количественные вычисляются заново по сохранённым данным.

Пункт 4 только подбирает ячейку и не резервирует вместимость. Пункт 5 повторяет
подбор, запрашивает подтверждение физического размещения и сохраняет его.
Каждую партию текущая версия размещает целиком в одной ячейке. Все принятые
партии должны быть размещены, прежде чем поставка получит статус `размещена`.
Недостаток места оставляет поставку в статусе `принята` до появления подходящей
вместимости и повторного выполнения пункта 5.

После операций 1, 2, 3 и 5 нужно ответить `да` на запрос сохранения в JSON.
Ответ `нет` отменяет все изменения текущей операции. Некорректные номера,
количества, даты, ссылки и форматы ввода приводят к сообщению об ошибке и
возврату в меню. EOF и Ctrl+C завершают программу без сохранения текущего ввода.

## Пример входных данных

Начальная поставка `D001` ожидает 10 единиц товара `P001`. Соответствующая
запись `DeliveryItem` в `warehouse.json`:

```json
{
  "delivery_item_id": "I001",
  "delivery_id": "D001",
  "product_id": "P001",
  "expected_quantity": 10,
  "actual_quantity": null
}
```

В алгоритм передаются ожидаемые и фактические позиции:

```json
{
  "expected_items": [{"product_id": "P001", "expected_quantity": 10}],
  "actual_items": [{"product_id": "P001", "actual_quantity": 10}]
}
```

Ожидаемый результат `compare_delivery_items()` — `[]`: количественных
расхождений нет. Для 7 единиц результат — недостача с разностью `-3`, для
12 единиц — излишек с разностью `2`. Дополнительные 3 единицы `P002`
дают расхождение `неожиданный товар` с разностью `3`; при сохранении
факта программа создаёт для него позицию с `expected_quantity: 0`.

## Воспроизводимый консольный пример

Перед демонстрацией сохраните исходный набор. В PowerShell из каталога `src/`:

```powershell
Copy-Item -LiteralPath data/warehouse.json -Destination data/warehouse.backup.json
```

Используйте исходный `warehouse.json`. Дата в примере фиксированная, чтобы
результат не зависел от дня запуска. Пустую дату в обычной работе программа
заменяет сегодняшней. На запросах ниже вводите значения последовательно:

| Шаг | Ввод |
| --- | --- |
| Пункт 2 | `D001`, документы `да`, дата `2026-10-28`, позиции `P001:10`, сохранить `да` |
| Пункт 3 | `D001`, качественное отклонение `нет`, согласование `да`, принято `10`, номер партии `DEMO-001`, срок годности пустой, сохранить `да` |
| Пункт 4 | партия `B002` |
| Пункт 5 | партия `B002`, физически размещено `да`, дата `2026-10-28`, сохранить `да` |
| Пункт 6 | просмотр результата |
| Пункт 0 | выход |

Результат: сопоставление выводит `[]`; создаётся партия `B002` количеством 10;
best fit выбирает `S001`, у которой перед операцией свободно 10 единиц.
Создаётся `PL002`; свободная вместимость `S001` становится 0, статус `D001` —
`размещена`. Повторное размещение партии отклоняется. Исходная история уже
содержит `B001`/`PL001` на 2 единицы, поэтому `capacity` этой ячейки равна 12.

Для повторения с нуля завершите программу и восстановите резервную копию:

```powershell
Copy-Item -LiteralPath data/warehouse.backup.json -Destination data/warehouse.json -Force
```

При повторной демонстрации используйте сохранённую исходную копию; не заменяйте
её уже изменённым набором. Резервный файл исключён из Git.
Проверки при разработке выполнялись на копиях и не изменили поставляемый набор.

Остальные независимые примеры перечислены в `data/demo_cases.json`:

| Поставка | Факт в пункте 2 | Результат |
| --- | --- | --- |
| D001 | `P001:10` | нет расхождений; ячейка S001 |
| D002 | `P001:7` | недостача 3 |
| D003 | `P001:12` | излишек 2; на исходном наборе подходит S002 |
| D004 | `P001:10,P002:3` | незаявленный P002, количество 3 |
| D005 | `P004:5` | сопоставление без отклонений; после принятия подходящей ячейки нет |

Примеры подбора независимы: предыдущие размещения изменяют свободную
вместимость. После принятия D005 используйте показанный программой `batch_id`
в пункте 4 или 5. Результат — сообщение об отсутствии подходящей ячейки;
запись `Placement` не создаётся.

## Пять основных функций

| Функция | Назначение и результат |
| --- | --- |
| `register_expected_delivery(data, delivery)` | проверяет клиента, товары, дату и неповторяемость позиций; создаёт Delivery и DeliveryItem; возвращает Delivery |
| `compare_delivery_items(expected_items, actual_items)` | возвращает список количественных расхождений, не изменяя входные данные |
| `register_discrepancies(data, delivery_id, discrepancies)` | связывает отклонения с DeliveryItem; возвращает сохранённые Discrepancy; повторная регистрация заменяет результат, не умножая записи |
| `select_storage_cell(product, quantity, storage_cells)` | возвращает исходный dict лучшей ячейки либо None; не изменяет вместимость |
| `register_placement(data, placement, required_zone=None)` | проверяет принятие, дату, остаток партии и доступность ячейки; сохраняет Placement, уменьшает вместимость; возвращает запись |

Вспомогательные `record_actual_receipt()` и `accept_delivery()` сохраняют
результаты физического поступления и согласованно принятые партии.
`record_actual_receipt()` возвращает идентификаторы обновлённых DeliveryItem.
`save_data()` проверяет данные, записывает временный JSON в том же каталоге и
заменяет основной файл через `os.replace`. Поэтому размещение и уменьшение
вместимости сохраняются вместе. Меню работает с копией состояния и применяет
её только после успешной записи. Одновременная работа нескольких процессов
с одним файлом не предусмотрена.

## Два алгоритма и сложность

`compare_delivery_items()` сначала для каждой из n ожидаемых позиций ищет
совпадающий `product_id` среди m фактических. Затем для каждой фактической
позиции вложенным циклом проверяет, была ли она заявлена. Нулевой факт по
непоступившей позиции учитывается как недостача. Разность равна факту минус
ожидание. Поиски завершаются при совпадении; в худшем случае выполняются
два прохода по n·m сравнениям. С учётом внешних циклов время
**O(n·m+n+m)**, при n,m ≥ 1 — **O(n·m)**; при одном пустом списке — линейное.
Рабочая память **O(1)**, возвращаемый список занимает **O(n+m)**.
Схема `models/algo_1.drawio` отражает четыре цикла C1–C4 и пять проверок.

`select_storage_cell()` один раз просматривает k ячеек, проверяя статус,
условия, необязательное ограничение зоны и вместимость. Выбирается минимальный
неотрицательный остаток `available_capacity - quantity`. При равенстве
остаётся первая подходящая ячейка. Время **O(k)**, дополнительная память
**O(1)**. Сортировка и список кандидатов не используются.
Схема `models/algo_2.drawio` отражает цикл C5 и семь проверок, в том числе
отдельно наличие ограничения зоны и соответствие зоны.

Оба алгоритма получают заранее проверенный вход: `product_id` уникален в
каждом входном списке; количества — положительные целые; пустые списки
допустимы. Для факта полного отсутствия позиции её не включают в `actual_items`.
В `expected_items` передаются только исходно заявленные позиции с ненулевым
ожиданием. Валидация ввода и сохранение вынесены из тел алгоритмов и не
включаются в указанные оценки их времени.

## Формат и правила данных

`warehouse.json` содержит коллекции `clients`, `deliveries`, `products`,
`delivery_items`, `batches`, `discrepancies`, `storage_cells`, `placements`.
Каждая запись — dict с атрибутами соответствующей сущности ER.
`demo_cases.json` содержит только сценарии вызовов и ожидаемые результаты,
а не дополнительные сущности. В рабочее состояние эти сценарии не загружаются.

По согласованному уточнению используется нормализованный состав спецификации:
в `Batch` нет `product_id`, он определяется через `delivery_item_id`;
добавлены `Batch.quantity` и `Product.allowed_zone`. Принятое количество
может быть меньше физически поступившего. Сумма партий позиции не превышает
её `actual_quantity`; сумма размещений партии не превышает `Batch.quantity`.
В консоли при одном подтверждении создаётся одна партия на каждую принимаемую
позицию; автоматическое разбиение на несколько партий или ячеек не выполняется.

Количество выражено в целых условных единицах; одна единица товара занимает
одну единицу вместимости. `storage_conditions` — один согласованный код
(`сухое`, `охлаждение`, `заморозка`). `allowed_zone` — один код зоны либо
`null`, означающий отсутствие ограничения. Даты — строки `ГГГГ-ММ-ДД`,
незаполненные значения — `null`. До поступления `actual_date` и
`actual_quantity` равны `null`; после приёмки количества заполняются и для
непоступивших товаров. Пара (`delivery_id`, `product_id`) уникальна.

Документы и результаты осмотра представлены на BPMN как объекты процесса.
Отдельный электронный архив документов не реализуется; количественный
результат хранится в DeliveryItem, принятое количество — в Batch,
качественные отклонения — в Discrepancy. Критические отклонения не считаются
урегулированными автоматически: требуется подтверждение сотрудника.

## Проверка данных перед загрузкой и сохранением

`validate_data()` отклоняет неизвестные статусы поставки и ячейки, а также
неизвестные типы расхождений. Статус поставки согласуется с фактической датой,
наличием принятых партий и полнотой размещения. Дата размещения не может
предшествовать поступлению. Для количественных расхождений вид и разность
проверяются по `actual_quantity - expected_quantity`; незаявленный товар
имеет нулевое ожидание и положительный факт. Качественное отклонение
требует непустого описания и нулевой разности. Эти проверки дополняют
контроль полей, PK/FK, уникальности позиций и ограничений количества.

Ошибка в рабочем JSON при запуске выводится как сообщение о невозможности
загрузки данных. При ошибке сохранения основной файл не заменяется.
Основные алгоритмы сопоставления и подбора ячейки не изменены.

## Уточнение проверки целостности

Перед загрузкой и сохранением проверяется закрытый перечень кодов условий
хранения: `сухое`, `охлаждение`, `заморозка` для товаров и складских ячеек.
Для поставок после проверки контролируется полнота регистрации количественных
расхождений: ненулевая разность факта и ожидания требует одной соответствующей
записи. Статус `проверена` допускается только при отсутствии отклонений.
Оценки сложности алгоритмов относятся к отдельным функциям при O(1) для доступа
к фиксированным полям записей и ограниченной длине идентификаторов, без стоимости
загрузки, общей проверки целостности и сохранения JSON.

На блок-схемах парные соединители K01, K02 и далее обозначают продолжение
одного потока в другом месте схемы. Входы в символы расположены слева/сверху,
выходы — справа/снизу; пары границ циклов C1–C5 сохранены.
