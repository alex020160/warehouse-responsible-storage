# Проверки исправлений по рецензии Софьи

Дата: 24.11.2026. Проверена Windows-сборка с Amazon Corretto 21.0.13.1.2
(javac 21.0.13.1) и Gson 2.13.2. Исходный warehouse.json не изменялся.

## Замечание #1 — повторные поля JSON

Issue: https://github.com/alex020160/warehouse-responsible-storage/issues/1

До исправления исходная строка с `"capacity": 999, "capacity": 20`
принималась. Теперь JsonReader в строгом режиме проверяет имена отдельно
для каждого объекта до создания JsonObject. Повторные поля отклоняются,
в том числе при одинаковых значениях и Unicode-экранировании имени.
Одинаковые имена в разных объектах допустимы.

В VerificationMain добавлены шесть проверок исходных строк: три варианта
повторного capacity, повторное поле корневого объекта, лишний документ
и незавершённый JSON. Правильный JSON проходит повторное чтение без изменений.

Из src/java при JAVA_HOME, указывающем на JDK 21:

```powershell
.\build.ps1 -Test
```

Результат: сборка успешна; 41 сохранённый сценарий Python/Java, шесть проверок
некорректного исходного JSON, JSON round trip и сохранность файла при отказе
записи прошли. Это локальная проверка автора исправлений, не повторная рецензия Софьи.

## Замечание #2 — дата проверяется до изменения Warehouse

Issue: https://github.com/alex020160/warehouse-responsible-storage/issues/2

До исправления прямой вызов registerExpectedDelivery с LocalDate.of(0,1,1)
выбрасывал исключение после добавления данных: поставок становилось 8 вместо 7.
Теперь используется та же IntegrityValidator.parseDate, что при загрузке JSON,
до первого изменения. Аналогичная защита добавлена для даты фактического
поступления, срока годности принимаемой партии и даты размещения.
Необязательный срок годности null остаётся допустимым.

Проверено через прямые вызовы сервиса, без защиты копией в консоли:
годы 0, −1, 10000 и null для ожидаемой поставки, факта и размещения;
годы 0, −1, 10000 для срока годности. Все 15 вызовов отклонены;
сериализация Warehouse до и после полностью совпала, целостность сохранена.
Годы 0001 и 9999 при регистрации ожидаемой поставки приняты.

Команда из src/java: `.\build.ps1 -Test` при настроенном JAVA_HOME.
Результат: JDK 21 успешно собирает код; 15 отказов без изменения состояния,
две допустимые границы даты, проверки #1, 41 сохранённый сценарий и JSON I/O прошли.

## Замечание #3 — полнота результатов перед zip

Issue: https://github.com/alex020160/warehouse-responsible-storage/issues/3

До исправления при 41 входном сценарии скрипт сообщал успех для 40, 0 и
42 результатов Java, а также для объекта вместо массива. Теперь до zip
проверяются тип массива, непустой набор сценариев и точное равенство
количества входов, результатов Python и результатов Java. Несоответствие
завершает процесс с ошибкой и диагностикой чисел. Содержательные различия
также дают ненулевой код независимо от включения assert. Старый отчёт
parity-results.json удаляется перед запуском, чтобы не оставлять ложный
успешный результат после отказа.

Небольшой стенд docs/verify_comparison_guard.py запускает реальную Java,
затем намеренно меняет выходной JSON перед его чтением compare_versions.py.
Проверки запускались на Python 3.13.7 и JDK 21 из корня репозитория:

```powershell
py -3.13 docs/verify_comparison_guard.py . "$env:JAVA_HOME/bin/java.exe"
py -3.13 docs/compare_versions.py . "$env:JAVA_HOME/bin/java.exe" work/parity
```

| Результатов Java | Ожидалось | Код завершения | Результат |
|---|---|---|---|
| 41 | 41 | 0 | Полная сверка принята |
| 40 | 41 | 1 | Неполный набор отклонён |
| 0 | 41 | 1 | Пустой набор отклонён |
| 42 | 41 | 1 | Лишний результат отклонён |
| Объект вместо массива | Массив из 41 результата | 1 | Формат отклонён |

Отдельный запуск без подмены вывода: 41/41 сценарий совпал, включая полное
состояние, чтение/запись JSON, ошибки данных и повторное размещение.
Повтор исходных воспроизведений #1/#2: повторное поле отклонено;
неверная дата отклонена, состояние совпало, поставок осталось 7.
